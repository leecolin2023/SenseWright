# 使用指南：怎样选择与使用 SenseWright

> **现行指南** · 本文提供可直接改写的提问示例。它们是任务意图示例，**不是必须复制的提示词模板**。执行细则参照四条 [活跃 Skill](architecture.md#7-版本和规范优先级)。

## 从任务目标开始

最简单的方法是先表达**你希望得到哪种认知结果**。

| 我想要…… | 选择 | 最小输入 |
| --- | --- | --- |
| 忠实读懂材料、厘清论证关系 | D | 原材料 + 希望完整覆盖还是聚焦核心 |
| 检查一项主张、方案或文档是否可靠 | R | 原材料 + 该材料要完成的任务 |
| 从现实问题真正学懂原理 | L | 学习问题 + 已知情境/原始资料 |
| 从一个主题主动找到下一研究问题，或在已有主干上继续研究 | P | 研究主题/已有主干 + 想达到的研究目的 |

如果没有现成的“知识主干”，可以直接提供此前的学习结果；材料不足时也可明确告知已有理解与不确定之处。不要伪造源码、实测或完整前置报告。

## D：深度阅读

**完整覆盖需求**

> 请使用 Deep Read 处理这份访谈材料。我需要在摘要中找到每个部门的独立诉求、问题、决定和后续动作。可以压缩语言重复，但不要将不同事项合并到看不见。

此时适用 **Coverage-Preserving**。它保留“全部独立认知单元”，而不是保留原文字数。

**理解主线需求**

> 请使用 Deep Read 处理这份技术书章节。我最关心作者如何从原始问题逐步推出设计选择；保留关键推导和有用的例子，删掉不改变整体理解的次要插叙。

此时适用 **Cognitive-Synthesis**。不是越短越好，尤其不能删除让陌生读者真正理解所必需的解释。

**D 的界限**：即使材料里有可疑数据，D 仍先忠实标示“材料称……”。如需核查，再明确要求 R 或新的研究任务。

## R：独立审阅

> 请使用 Review 审阅这份系统需求说明，重点是它是否足以支持实施。先覆盖业务规则、流程状态、权限、例外、接口和附录，再只报告会影响实现或验收的重要缺陷。

> 请使用 Review 审阅下面的观点文章，区分事实、因果推断、替代解释与证据缺口。不要把它改成工程项目审计。

R 的原子审阅单元按语义划分，不按标点数拆句。全覆盖是**审阅范围**；重点输出是**报告方式**。

## L：系统学习

> 使用 Learning 研究“为什么相同模型在不同 Agent Harness 中，工具调用成功率差异很大”。从真实调用链出发，对照系统提示、工具 Schema、模型输出、执行反馈等机制；有源码证据请给出实际位置，不能用推理冒充运行结果。

> 使用 Learning 研究“中国模型公司的收入问题主要是不是内需”。请先区分购买数量、实现价格、价值分配与成本，再寻找能区分竞争解释的数据。没有行业可比数据时明确指出不能裁决的部分。

L 的工作重点是**形成解释力强、证据对齐、可迁移的理解**。当前 [Learning V0.7.0](../skills/system-learning-v0.7.0/SKILL.md) 以 R00–R15 条完整规则组织，每条包含「为什么、怎么做、例子、怎么检查」，把验收和定向修复放在规则内部。它可能校准问题，也可能保留用户原有精确问题，不会为了“看起来深入”强行往上抽象。

**关于前置步骤**：只要本轮任务确实调用 L，就依照 [D/R→L 独立编排](architecture.md#4-learning-的独立前置) 执行。没有宿主隔离调用记录时，只能说明方法预期，不能宣称隔离已经在技术上得到验证。

## P：从主题或已有理解主动发现问题

> 我想研究模型服务平台，但尚未选定实践问题。请用 Practice 先分析它为业务解决什么问题，稳定调用模型依赖哪些机制，以及哪些条件变化或运行约束可能暴露关键问题；给出有区分度的候选问题，并说明为什么优先研究“Qwen 原本正常、后来突然无法调用”或为什么应选其他问题。情境是假设时请明说。

> 我已经理解 Agent 的 Tool Call → Execution → Observation。请用 Practice 检查这条主干缺少的必要前提：模型为什么决定使用工具、如何知道工具能力、如何选工具和构造参数。再找出其他有独立研究价值的问题，并展开其中最重要的几个。

> 我已经理解有效需求和收入的基本关系。请用 Practice 检查原 Learning 是否混淆了价格降低导致的需求量增加与需求曲线变化，并发现价值捕获、单位经济性和商业模式等值得独立研究的问题。

> 我已经理解模型服务的调用链。业务反馈“Qwen 昨天能用、今天无法调用”。请用 Practice **先界定真正需要诊断的问题**：具体表现、影响范围、时间条件和可追踪证据；再选择最能区分原因的第一项检查，沿结果逐步缩小范围，解释相关运行机制。没有真实日志不要断言 GPU 或引擎故障。

**从主题生成问题**与**从故障现象诊断原因**是两个不同层次：前者先从系统的现实目标、必要机制与关键约束找出并挑选值得研究的场景，后者是在已经选定故障后用证据缩小原因。生产排障是 Practice 的一种**按需深入方式**：先把笼统反馈转为可诊断的问题，再用有区分力的检查缩小竞争原因。只有单一故障任务时不强制审计整套平台；全面研究技术时也不能只挑一个下游故障。

P 的重点是**先发现值得问的问题，再问透重要问题**。可提供问题地图、辩论式推演、面试深追或真实应用，但不强制“每个术语出三道题”或“所有研究都产出代码”。

如果要求实操，可进一步指定具体目标、权限和环境；但**只是提出实践任务**并不意味着仓库能够自动运行代码或操作外部系统。

## 常见组合与边界

**“请总结并审阅”**：可以分别做 D 与 R。R 直接读原文，不能只审 D 的摘要。

**“请先学习，再找深层追问”**：按本轮 D/R→L 完成 Learning，再根据已有知识结果进入 P。P 是否进行由用户目标决定。

**“我只问一个概念”**：如果目的只是简洁解释，不必强制把回答扩展成完整项目或问题网络。

**“请用 Practice 给我评分”**：用户没有现场作答或可核验操作记录时，模型自答只能算示范，不能当作用户已掌握的依据。

**“请确认是否真正执行了三条模型调用”**：必须有宿主运行记录；章节标题、同一答案中的角色扮演不构成独立性证据。

## 如何读结果

一次高质量交付不必每次包含表格或固定章节，但应该让你判断：

- D：核心结构、事项与推理是否仍能从结果追溯到原文？
- R：重要问题的判断是否建立在足够范围的审阅上？
- L：解释能否回答真实问题，例子是否真的支持该结论？
- P：是否发现主干遗漏、开辟了有价值的独立问题线，并对重点问题做了实质性推演？

不了解证据时可以明确标注未知；好的知识工作允许“尚不能裁决”，不允许把不确定性伪装成已经执行与验证。
