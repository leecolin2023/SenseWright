## 1. 根因审计

四次修复都在解决局部真实问题，但每次把**某一任务的研究技巧**追加成核心步骤，造成三种架构失衡：

1. **错误的知识所有权**：金融估值、行业知识或银行流程本应来自领域资料/工具/模型本身，而不是成为所有领域的 Skill 指令。通用 Skill 规定“何时发现相关理论、如何核对及运用”，不规定“必须运用哪个理论”。
2. **错误的步骤所有权**：Ground、Domain Anchor、Problem Discovery、Problem Chain、Reality Calibration 并非每道学习题的一组连续工序。有些问题已被正确界定；有些需要先比较再发现理论；有些只是做一条源码追踪。流程应允许循环、跳过、退回。
3. **错误的成功判据**：曾先后把“机制链完整”“产生深问题”“找到价值终点”当成成功，而没有稳定检验**用户究竟学会了什么、哪些结论因实际证据改变、能否迁移到邻近问题**。

## 2. 稳定核心与案例知识分层

### Runtime 核心只有一组通用认知责任

- **Orient**：识别用户想理解什么、真实对象是什么、已有事实和被选择的样本是什么；任务目标不等于某个容易获得的指标。
- **Frame**：动用领域相关且有适用前提的知识，必要时发现、比较和修正问题。深度用解释增益与证据区分衡量，不用抽象程度衡量。
- **Explain**：用最少必要机制说明为何与如何，从具体失败/条件推进；不为了显得完整延长问题链。
- **Anchor**：把关键结论对应到原始资料和可观察行为；按需使用数字/执行路径/状态转移/对照研究等任何适当的证据，不强制统一模型。
- **Challenge / Rebuild**：用反例或条件变化暴露边界，修正起点和结论；整合成读者能迁移的解释，及时停止。

这些是**质量责任**而非可观察的五次模型调用。研究顺序以证据为先，呈现顺序以读者理解为先。

### 不再写进通用 Skill 的内容

- 股票估值的FCFF、FCFE、DCF、贴现率与股价隐含预期；它们只应在**投资/股权价值**任务出现，且要区分企业与股权现金流、内在价值与交易价格。
- 银行业务的审批—签约—生效状态规则；只在对应银行任务提供具体例子或运行证据。
- 医疗临床分级、Linux进程与代码Agent工具调用链等领域细则；具体实现仍需要可查源码、临床/原始资料和适用的证据等级。
- 强制数字估计、固定模板化问题目录、所有题目都要一个“根本性价值终点”。有的主题是解释、鉴赏、形式证明或多目标辨析，无单一可量化目标。

### 不改变但要单独审计的内容

`SKILL.md` 仍要求 **D 和 R 两路独立且同源的前置工作**。这是宿主执行策略，与“如何学习”的认知内核分开。简单问题的计算/Token 开销可能过高，但此轮不在没有真实 Trace 和行为测试时擅自改成可选；要把运行时开销、前置隔离正确性列入独立架构评估。

## 3. 结果的最低质量定义

好的 Learning 不是“讲了很多”：
- 能让读者用自己的语言解释至少一个真正重要的关系、差异或条件；
- 对重要结论能指出适合这个领域的来源或行为证据，已核验与未知分开；
- 能解释一项相邻变化，或知道什么观察会使原理解需要修改；
- 不改变用户原本任务，不因为一项领域知识恰好被写进 Skill 就强行挪用；
- 简单任务短答，复杂任务深入，严格区分教学推演和已经发生的实测。

## 4. 回归测试与反过拟合

**保留历史 #1–50**，但将针对具体股票/银行/Agent结果的 assertions 视为领域 fixture 的期望结果，不是通用执行条款。新增 #51–58 选择尽量不重复前面金融案例的领域：
- 统计相关性与因果；
- 历史史料冲突；
- 法规条文与例外；
- 代码运行与源证据；
- 多目标的产品设计；
- 数学定理证明与适用条件；
- 文学文本解读，防止强行统一可量化终点；
- 精确概念小问题，防止过度深读。

测试必须同时检查**保留专项深度**：旧的股票估值 #47–48、程序链 #31–35、银行流程 #38、健康证据 #39 和“跳过” #41/#46/#50，不得因移除硬编码知识丢失。对模型是否真的理解、是否产生良好问题，必须做匹配模型调用的 A/B，不能用测试脚本结构通过冒充语义能力通过。
