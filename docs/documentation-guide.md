# SenseWright 文档维护约定

> 本文是维护说明，不是第五条 Skill，也不修改四条 Skill 的执行方式。

## 一、文档分层

| 层级 | 存放位置 | 应回答什么 |
| --- | --- | --- |
| 现行执行规范 | 根 `SKILL.md`、`skills/*/SKILL.md` | 任务如何路由、每条 Skill 的职责和底线 |
| 项目首页 | `README.md` | SenseWright 是什么、适合谁、怎样开始 |
| 现行解释文档 | `docs/architecture.md`、`docs/usage.md`、`docs/README.md`、`evals/README.md` | 当前机制、边界、使用、评测 |
| 历史审计和设计 | 历史 `docs/learning-*`、`docs/practice-*`、`evals/HISTORY.md`、`CHANGELOG.md` | 当时为何这样改、留下了什么教训 |
| 评测事实与材料 | `evals/*.json`、`evals/fixtures/`、`scripts/` | 可运行或可人工审阅的样例、基线与工具 |

文档中出现旧版本的 Gate、阶段、产物清单或具体行业算法，不等于它们在当前版本仍是必经步骤。

## 二、修改原则

1. **先校准现行 Skill。** 每次修改首页或说明，核对四条活跃 Skill 的真实文本、根路由、版本号、职责和执行边界。不能仅凭历史设计文档推断规则。
2. **以中文解释为主。** 专有名词（Deep Read、Review、Learning、Practice、Raw Input、Coverage-Preserving 等）首次出现时用中文解释；代码接口、命令、路径和源文件名称保留原样。
3. **不给执行方法凭空加步骤。** 解释文档不创造新的“所有任务必走流程”“固定表格”“统一问题数量”，除非现行 Skill 确实要求。
4. **保留研究证据。** 失败案例、设计变更与旧方法可以留在历史资料中，但标注“历史”及当前有效的规范链接。历史内容错在当时，可以用编者注释指出，不用静默篡改成当年没有得出的结论。
5. **证据级别诚实。** 不把源码阅读当作运行实验，不把结构校验当成模型回答质量测评；没有 Trace 就不声称 D/R 运行时独立。
6. **用户目标优先。** 示例是帮助读者理解路由，不是用大量案例覆盖全部领域，更不是把金融、银行或 Agent 专项实现写入通用 Skill。
7. **更新导航和回归。** 新增现行文档时更新首页与 `docs/README.md`；触及方法职责时同步核对路由与用例，但不要为了适配新实现删除历史失败案例。

## 三、文档审查清单

一次文档 PR 至少检查：

- 四条链接均指向当前活跃版本，旧 Practice V0.2 没被写成默认；
- D/R 独立、同源、完成屏障与宿主 Trace 的限制没有被遗漏；
- Deep Read 的双压缩契约、Review 的先覆盖后重点、Learning 的自适应与证据对齐、Practice 的枝干探索均描述准确；
- 项目首页、架构与使用指南彼此不矛盾；
- 相对链接确实存在，章节锚点尽量采用稳定标题；
- 评测数量从实际数据统计，不凭过去文档中的数字；
- 新增案例没有被误写成固定执行规范。

## 四、可用的本地检查

在仓库根目录运行：

```bash
python scripts/validate_skills.py
python scripts/validate_evals.py
```

这些脚本只覆盖既定的结构合同；文档内部链接、历史事实准确性、叙述与 Skill 是否一致仍需专门检查。若声称行为提升，必须另外提供同条件的实际模型评测及人工复核。

## 五、历史文档的标准说明

适用于复盘文档的简短标记：

> **历史设计记录（非现行规范）**：本文保留当时的研究问题、方案和验证边界。相关规则后续可能已重构；当前执行以根 `SKILL.md` 和对应活跃 Skill 为准。

不要为每份历史文章反复复制当前全部规范；通过 [文档索引](README.md) 进入即可。
