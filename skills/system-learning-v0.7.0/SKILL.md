# System Learning V0.7.0 — 从问题建立理解的完整规则

## 目标

帮助用户理解事物的**原理、组成、运行过程和因果关系**，使其能顺着知识主干理解“是什么、怎么运作、为什么如此”，必要时再理解适用边界和变化条件。

**学习解释优先于论证审计。** 成熟理论、标准定义、教材或官方说明能够解释的知识，应优先准确引用和通俗转述，不凭空发明理论。Learning 不要求每个概念都包装成一个新问题，也不要求所有教学推导达到生产验收标准。

**主干优先，偏差分级。** 只有会推翻核心原理、主要因果关系或重要适用条件的事实缺陷，才作为关键问题要求修正；不影响主干的近似、措辞或局部精度问题，简短标注或顺手修正即可。不得以主干优先为由掩盖实际重大错误、把教学假设冒充生产实测。

Learning 的完成标准是机制是否解释透彻、推导能否被读者跟上，而不是文章足够短、足够“问题驱动”、证据审计足够全面。

**本 Skill 是完整的规则系统。每条规则按「规则 → 为什么 → 怎么做 → 例子 → 怎么检查」组织。** “怎么检查”是规则自身的验收条件；未通过时修复相应认知缺口，而不是机械增加篇幅或术语。例子用于解释规则，不是所有任务必用的行业模板。

以下规则按学习工作的自然关系组织，但不要求最终文章按规则顺序写作，也不要求所有任务使用相同篇幅或例子。**定义→组成→原理→步骤→示例**本身就是合法且常见的学习讲法；对照、追问、条件变化和实测验证按实际需要触发，不能把缺少这些附加形式视为学习失败。

## 第一部分：准备与确定学习目标

### 规则 R00：先独立理解和审阅材料，再开展 Learning

**为什么：** 直接根据原材料生成学习文章，容易沿用原作者的组织结构、遗漏论证缺陷，或者把作者的观点当成已经验证的事实。

**怎么做：** 根据 SenseWright 总入口的执行要求，本轮 Deep Read 和 Review 分别独立处理相同原始输入。两者完成后，Learning 再读取原材料及其结果。Deep Read 提供原文结构，Review 提供待核实的疑点，但两者的分析本身不能充当新的事实证据。真正的独立运行需要宿主执行器保证。无独立文档而只有问题时，D/R 可轻量完成，不得虚构原文或问题。默认只交付整合后的 Learning 解释。

**例子：** 学习 vLLM 视频时，Deep Read 还原视频如何从 KV Cache 讲到 PagedAttention；Review 检查视频的性能倍数、参数解释及结论适用条件；Learning 再根据用户的问题重新组织知识。

**怎么检查：** 检查本轮是否存在独立 D/R 执行记录及明确的结果交接。仅仅读取两份 Skill 文件或在最终文章中写出 D/R 标题，不算执行成功。缺少执行记录时不得声称已验证完整流程；不可用历史 D/R 代替本轮。

### 规则 R01：先确定用户真正想理解什么

**为什么：** 原材料的主题、作者介绍的内容和用户想获得的理解，可能是三件不同的事情。混淆它们容易把 Learning 写成原材料总结。

**怎么做：** 明确用户提出的问题、研究对象以及理解完成后希望具备的判断能力。用户已经给出具体问题时，不擅自扩大；用户只有宽泛主题时，可以从材料和上下文中识别合理的学习重点，并说明边界。

**例子：** 用户提供一篇介绍 vLLM 的视频，重点想知道为什么同一张 GPU 能处理更多请求。学习目标便是解释并发处理能力的来源，而非掌握视频提及的所有参数。

**怎么检查：** 阅读成稿后，能否指出哪些内容直接回答了用户问题？如果删除大部分章节后仍不影响核心回答，说明文章把原材料的内容范围错当成了学习目标。

### 规则 R02：区分研究目标、观察指标和材料选择

**为什么：** 用来观察问题的数据，不一定直接代表真正关心的结果。只检验容易获得的指标，可能得出错误结论。

**怎么做：** 遇到涉及数据、实验或比较的学习任务时，分别识别要解释或验证的目标、用于判断的指标，以及所选材料或样本能够代表什么。只有这些区别影响结论时才展开，不为简单概念强造指标。

**例子：** 为研究模型服务能否承载更多真实用户，只测极短 Prompt 的输出 Token 吞吐，不能直接代表长 Prompt、复杂业务负载下的整体服务能力。

**怎么检查：** 把文章的结论、所用指标和样本条件并排比较：这些指标真的能够代表结论吗？如果换成另一个合理的样本范围，结论可能明显不同，就应补充适用条件或修改表述。

### 规则 R03：保留有价值的问题，只修正真正妨碍理解的问题

**为什么：** 模型容易为了显得深入，不断把具体问题改写成越来越宏大的问题，反而远离用户原本想知道的事情。

**怎么做：** 检查当前问题是否明确、可解释且有研究价值。若问题已经准确，直接回答。若问题包含未经证实的原因、混淆了不同对象，或无法区分重要结果，才根据已有事实重新界定。

**例子：** “为什么模型昨天能调用，今天不能调用？”是值得研究的现象，但不能直接改写成“为什么 GPU 故障了”。GPU 故障只是许多可能原因之一。

**怎么检查：** 比较原始问题和最终解释：有没有未经必要而改变研究对象？重新表述之后，是否能指出原问题的具体缺陷？如果不能，就不应强行重构问题。

### 规则 R04：优先采用成熟理论和官方解释建立知识主干

**为什么：** 既有理论与权威机制说明往往已经形成清晰的概念和解释。临时发明术语或推导框架，可能增加理解负担并引入错误。

**怎么做：** 优先依据公认基础理论、教材、技术标准、官方文档说明定义、构成和机制；再用清晰语言解释实际如何运作。区分普遍原理与某产品、版本、硬件的具体实现；只有已有解释无法覆盖关键环节时再补充推导，标明推论边界。引用不是堆积资料，真正重要的是把已有解释讲明白。

**例子：** 解释模型显存时，依据参数精度、注意力缓存与推理调度的成熟机制；判断 Qwen 混合架构或 vLLM-Ascend 的特定适配时，再参考各自官方技术说明，而不是自行设计一种通用“卡数理论”。

**怎么检查：** 核心概念是否符合成熟知识、关键机制是否讲清？如有具体实现的强断言，是否有合适依据？若缺少某个不影响主干的非关键引用，不据此否定整篇学习文章。

## 第二部分：让知识逐步形成理解

### 规则 R05：保留理解机制需要的知识厚度，而非机械删减

**为什么：** 合理的背景、术语解释、例子和重复，有助于读者理解抽象机制；把“是否属于最短答案”作为删减标准，容易丢失必要的推导中间层。

**怎么做：** 以清楚的知识主干组织内容，保留帮助读者理解组成、条件、执行过程、因果变化和具体例子的部分。允许完整的分步骤说明及有价值的延伸。只删明显无关或反复陈述而不增加理解的内容；不按知识点数量、篇幅或每段是否直接回答问句来判定好坏。

**例子：** 容量规划依次介绍权重、运行时资源、软件适配、TP、吞吐及副本数，即使各章节包含必要基础概念，也是完整解释，不应仅因某章节没有单独引出业务问题就删除。

**怎么检查：** 读者能否顺着知识前提复述实际机制？某个段落的删除是否造成中间步骤缺失？只在内容确实打断主干时做减法。


### 规则 R06：按自然的原理与步骤顺序讲解，不强制问题驱动

**为什么：** 许多知识适合直接按定义、组成、工作原理和执行过程解释。强行为每个新概念制造障碍或故事，反而打断原有逻辑。

**怎么做：** 优先选择概念依赖、因果先后或操作流程本身提供的自然顺序。某个设计动机确实有助理解时，简要解释它解决了什么限制；动机不是必要条件时直接讲解原理，不必在每小节先设问。对于计算、部署与业务流程，分步骤往往正是合适结构。

**例子：** 可以直接从权重显存，讲到请求状态变化、模型并行方式、吞吐与实例数量；不需要先给每个环节设定一个虚构故障。

**怎么检查：** 读者能否跟随步骤理解事情如何发生？如果可以，不得仅因其是顺序说明而评价为“不够问题驱动”。只有缺少动机真实妨碍理解时，才补充最小问题背景。


### 规则 R07：解释机制时，讲清楚条件如何导致结果

**为什么：** “某技术能够提高性能”“某规则能够控制风险”只是结果声明，没有解释作用机制。

**怎么做：** 对重要机制说明：起始条件是什么，哪些对象参与，发生了什么动作或状态变化，为什么会产生相应结果。技术问题按需追踪调用、数据和状态；业务问题按需追踪条件、责任和规则。不要把先后发生直接当成因果关系。

**例子：** 解释 PagedAttention 时，要从请求增长导致 KV Cache 需求增加开始，说明缓存块如何按需分配、逻辑块怎样映射到物理显存，以及为什么由此减少预留浪费。

**怎么检查：** 只看文章的机制解释，能否复述从条件到结果的必要过程？如果只有“使用 A，所以 B 更好”，却无法说明 A 改变了什么，就不算解释完成。

### 规则 R08：把容易混淆的机制放在同一问题下比较

**为什么：** 多项技术可能都声称提高性能、改善可靠性或降低成本。如果只介绍各自优点，读者很难判断它们什么时候有效、有什么不同。

**怎么做：** 找出不同机制面对的共同目标与不同约束；在条件可比的情况下，说明它们分别改变什么，以及解决一个问题为什么不代表另一个问题也得到解决。没有实质差异时，不为比较而比较。

**例子：** PagedAttention 改善 KV Cache 的显存管理，Continuous Batching 改善多个请求共享推理执行机会的方式。显存足够而请求仍逐条执行时，缓存管理并不能代替批处理。

**怎么检查：** 给出一个条件变化，文章是否能够支持读者区分应该关注哪种机制？如果只能分别背诵定义，却无法判断它们的适用条件，说明关系没有讲清。

## 第三部分：让知识对应可核实的现实

### 规则 R09：依据与解释层级相符的知识来源，严守关键事实边界

**为什么：** 一般理论的教学解释与特定产品能否达到生产性能是两种不同主张。把所有原理都要求生产级验证，会让 Learning 沦为工程审计。

**怎么做：** 通用原理优先引用成熟理论、教材、标准或官方说明；特定产品、版本、兼容性或实际性能的强断言，才根据重要性核对官方文档、源码、日志或测试。优先修正能改变核心机制、主结论或重要适用边界的事实问题。教学估算只要条件清晰且未冒充真实测量，就可以承担解释功能。

**例子：** “BF16 参数通常占两字节”可以由数值格式原理说明；“某模型在指定 NPU 的 TP=1 部署已经稳定通过压测”则需对应版本和测试证据。缺少后者不会推翻前者。

**怎么检查：** 是否存在足以推翻核心解释的关键无据事实？没有时，不因为尚未进行全量生产测试而判学习主干不成立。


### 规则 R10：明确例子是在帮助理解，还是在验证结论

**为什么：** 一个例子可能非常直观，却不足以证明整项技术在真实环境中的性能或可靠性。

**怎么做：** 使用例子前明确其作用：帮助建立直觉、演示机制，还是检验一项判断。教学假设应明确标示，不能把示意计算或模拟过程写成实际测量。

**例子：** “每块放 4 个 Token，7 个 Token 需要 2 块”可以帮助理解按块分配，但不能由此证明 vLLM 在真实 GPU 上实现了几倍吞吐提升。

**怎么检查：** 把案例能够直接得出的结论和文章声称证明的结论分别写出。两者是否一致？如果案例只说明分块原理，却被用于证明真实吞吐提升，就必须缩小结论或补充证据。

### 规则 R11：仅在不同解释会改变关键结论时要求区分性证据

**为什么：** 对照实验适合裁决争议，而非每一篇介绍成熟机制的学习文章都必须竞争假说、设计实验。

**怎么做：** 只有两个解释会产生不同的核心机制、重要判断或实践结论，且现有依据不能区分时，才寻找能产生不同预测的事实或对照。解释成熟原理时可以直接采用现有知识与教学推导；对仍待实测的产品性能应如实保留边界，但不将“未实测”解释为“原理没有讲清”。

**例子：** 解释 TP 如何切分单个模型实例，无须先运行全部并行组合；只有断言“特定负载下 TP=4 必然比双 TP=2 更好”才需要可比的实测或收缩结论。

**怎么检查：** 是否存在真正能改变主线的竞争解释？没有就不强制实验；有则检查证据够不够支撑关键判断。


### 规则 R12：发现偏差时按其对机制主干的影响修正

**为什么：** 修正重大错误是必要的，但让细小精度问题主导整篇审阅，会丢失学习的主要解释对象。

**怎么做：** 区分三类问题：①推翻核心原理、因果关系或主结论的错误，必须纠正；②误导重要条件或实际选择的缺陷，局部修正和限定；③不改变推导主干的局部口径、四舍五入或表述问题，简要指出即可。不得把真实重大错误伪装成无关细节，也不得凭空编造自洽理由。

**例子：** 把 TP 说成独立模型副本，是核心机制错误；显存示例中的单位口径若不改变“权重之外还需要运行资源”的教学结论，应统一单位，但不宜据此整体否定容量规划的机制主线。

**怎么检查：** 该缺陷会使读者错误理解核心机制，还是只需局部修正？将报告强度与实际影响对齐。

## 第四部分：组织学习成果并完成验收

### 规则 R13：优先保护连贯的知识顺序，不强制改成问答结构

**为什么：** 对操作原理、技术计算和系统流程，按步骤讲解常常是理解上的最佳顺序。研究资料的原顺序不一定有问题。

**怎么做：** 检查定义、前提、组成、机制、计算与结论之间的依赖是否清楚。若原结构已经连贯，就保留；如果确有跳步或前提后置，再局部调整。贯穿案例、技术章节、公式步骤或问答结构均可，不因形式差异要求重写全文。

**例子：** “查模型规格→算权重→估运行时资源→确认适配→压测单实例→估副本数”是容量规划可理解的自然顺序，不需要变成连续的故障悬念。

**怎么检查：** 读者能否沿文章从已知条件走到结论？能则认可。章节具有一定独立性不等于术语堆砌。


### 规则 R14：优先检查能否理解与复述机制，迁移测试按需使用

**为什么：** 迁移到新情境有价值，但不是所有原理讲解都需要另设考题。强加新问题和反例可能把学习变成验收测试。

**怎么做：** 首先判断文章是否足以让读者解释关键对象的组成、运行过程与因果关系。仅在用户的学习目标包含复杂方案判断、机制比较或容易混淆的条件迁移时，再补少量变化场景；如果原文已经用连贯的示例讲透，就不要求文末额外设置题目。

**例子：** 理解卡数规划的权重、运行资源、软件条件、吞吐和实例关系，已经是有效学习成果；若还要比较真实四卡架构，再展开 TP=4 与两个 TP=2 副本的对照。

**怎么检查：** 文章是否能支撑读者顺着原理复述和理解过程？如果是，不因为缺少新情境练习而判不合格。模型自检不能证明真实用户已经掌握。


### 规则 R15：达到当前学习目标后停止，并保持任务边界

**为什么：** 模型容易把继续扩展知识、提出新研究问题或规划实施当成更深入的学习，最终使文章偏离用户目标。

**怎么做：** 核心问题已经得到充分解释，关键依据和边界也已明确时，停止当前学习。其他值得研究的内容可以简短指出，但不默认展开。保持用户授权边界，不把知识解释擅自变成工程实施、投资决策或其他行动。通用规则不应内嵌某个行业的固定方法。

**例子：** 已经解释清楚 PagedAttention 和 Continuous Batching 为什么可能提高单卡吞吐，就可以结束当前文章；GPU Worker 的进程架构与多机分布式推理可以留待以后研究。

**怎么检查：** 删除末尾的扩展内容后，核心理解是否受影响？如果不受影响，就考虑停止或拆分。还应检查是否未经用户要求提出了具体实施承诺、投资判断或其他超出学习范围的结论。

## 使用与验收原则

这些规则约束 Learning 的认知工作，不要求把十六条规则逐项打印在最终文章中。**按步骤、按结构、按经典理论展开的文章，不因缺少连续设问、对抗验证或额外练习而降低评价。**

简单任务可以用很短的解释满足多个规则；复杂研究可以根据证据和反馈反复调整。需要对照或验证的规则应按实际问题触发，不能为完成规则而虚构实验。

每条规则中的“怎么检查”都是相应工作的验收要求。检查发现失败时，优先修复具体缺口：

- 学习目标不清楚：重新界定问题。
- 缺少必要前提：补充解释。
- 知识确实无关并打断主线：删除或移出；有助于理解的铺垫应保留。
- 核心机制无法解释结果：补齐必要的因果过程。
- 证据足以推翻关键结论：修正或收缩；教学近似与局部差异按影响程度处理。
- 读者无法沿原文复述主要过程：补上缺失的前提与中间步骤；迁移练习仅按需增加。

Learning 自身的检查不能代替独立审阅，静态文档检查不能证明真实用户已经学会。凡是声称独立执行、实际测试或用户掌握情况，都需要相应的可核查证据。

**最终交付标准：优先采用成熟理论或官方解释，清楚、连贯、充分地说明事物的原理和运行过程，保留关键推导主干；只有会改变核心理解的证据问题才构成主要障碍。根据学习目标按需补充比较与迁移，不以问题驱动、实验数量或非关键细节的绝对精确作为强制门槛。**
