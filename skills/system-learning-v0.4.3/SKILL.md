# System Learning V0.4.3 — Knowledge → Gap → Use

## Suite 集成边界

本 Skill 在 Document Intelligence Suite 中承担 **L — Learning**：目标是形成用户自己的知识模型，而不是忠实复述原材料，也不是评价文档质量。

- 若用户主要问“原文讲了什么”，交给 Deep Read。
- 若用户主要问“这份材料哪里有问题”，交给 Review。
- 若用户主要问“我应该怎样理解、学会并使用它”，使用本 Skill。
- 与 Deep Read / Review 联合执行时，尽量直接读取原始材料，不依赖其他分支的结论。
- 当用户指定以附件/材料为学习基础时，材料未支持的内容不得静默用常识补齐；只有在用户要求研究、核实、扩展时才引入外部信息，并明确区分。


## 目标

> 学习不是把材料解释完，而是形成一套自己的知识模型，并让这套知识能够继续进入真实问题。

只保留三层：

`Build Model → Find Gaps → Project to Use`

不要为了完整增加阶段，不要把内部思考框架机械展示给用户。

---

# 一、核心原则

## 1. 不要孤立解释知识

把概念放回系统、关系、事件和状态变化中理解。

优先回答：

> 它为什么出现？在整个系统哪里？一件真实事情发生时它做了什么？做完以后什么发生了变化？

## 2. 不要服从原材料结构

材料只是输入，不是最终知识框架。

如果存在混层、简化、错误前提或不稳定分类，应保留有价值内容并重新组织。

发现问题后不能只批判，还要建立更好的替代模型。

## 3. 先解释对象，再抽象方法

抽象不能替代对象知识。

先回答：

> 我现在怎样理解这件事、这个人物、这个案例或这个系统本身？

只有当材料自然暴露出更通用的方法时，再继续上提。不要为了泛化而牺牲当前对象的知识密度。

对于方法论型知识，对象与方法可能天然重合；对于人物、事件、案例等对象型知识，应优先保留对象模型，再决定是否形成可迁移的方法。

## 4. 先验证命题，再解释命题

当输入是一个问题、观点或反常识命题时，不要默认其中的前提已经成立。

先区分：

- 用户真正观察到的现象；
- 问题中夹带的未经验证前提；
- 哪些部分可以靠结构推理澄清；
- 哪些部分必须依赖数据、史料、案例或外部证据确认。

优先把问题改写成真正需要解释的对象，再进入机制分析。

> 先确认“发生了什么”，再解释“为什么会这样”。

不要为了回答得快，把一个有待验证的假设直接写成事实。

## 5. 如果命题被改写，后续知识结构必须跟着重建

命题检查不是回答前的附加前言。

如果检查后发现真正的问题已经改变，后续解释必须围绕新问题重新组织，不能继续沿用原问题的原因清单。

例如：

`“A 为什么这么少？”`

如果最终发现真正的问题是：

`“从 X 到 A 的转化过程中，损失主要发生在哪一层？”`

那么后续结构应围绕“转化链、瓶颈和各层损耗”展开，而不是继续罗列“A 少的五个原因”。

> 命题重写必须触发知识重构，否则命题检查只是装饰。

## 6. 个人笔记不是摘要，而是当前最好的认知版本

一次完整学习应尽量留下独立成立的 Knowledge Note：

> 如果半年后重新看这个主题，我希望留下哪套模型帮助自己继续判断和行动？

不要按原文目录或聊天顺序压缩。

## 7. 不要把“能讲清楚”当成“已经学会”

模型形成后，内部检查：

> 哪些地方已经能解释，但还不会真正操作、验证或做决策？

只找会阻塞下一步的关键 Gap，不生成课程进度表。

## 8. 知识最终要进入使用

同一个 Knowledge Gap，应根据用户下一步目标转换成不同产物，而不是为每个场景建立新 Skill。

# 二、Build Model

Build Model 是主体，具体组织由知识本身决定。默认先建立“对象本身的模型”，再判断是否值得上提为更通用的方法。

通常需要完成以下认知动作中的若干项：

### 命题检查

如果输入本身是一个待解释的命题，先问：

> 我真正观察到了什么？其中哪些只是我已经默认成立的解释或前提？

必要时先把命题拆成可验证部分，再决定真正的解释对象。

如果命题检查导致问题被重新定义，立即围绕新问题重建后续结构；不要把新问题只写在开头，正文却继续回答旧问题。

例如：

`“A 为什么这么少？”`

不能直接进入原因列表，应先确认：

- A 是否真的少；
- 相对于什么基准说“少”；
- 用户看到的是总量、存量、幸存者，还是被记录/被记住的结果；
- 是否存在分母、口径或选择偏差。

### 定位

用简洁语言钉住：

> X 本质是什么，它解决什么问题。

### 放回大图

恢复真正相关的上游、同层和下游关系。

如果原材料把不同层级并列，重新分层。

### 让事情跑起来

对于动态知识，优先使用一个真实事件载体：一笔业务、一次审批、一个 Agent 任务、一次模型运行、一个事故或一次制度触发。

关注：

`触发 → 判断 → 动作 → 状态变化 → 反馈 → 下一步`

### 追到底层机制

流程说明“发生了什么”，机制说明“为什么这样工作”。

优先寻找真正决定行为的机制，如控制权、权利成立、风险计量、信息验真、状态拥有、资源占用、反馈和失败恢复。

### 必要时纠偏并重构

检查是否存在：

- 不同层级被并列；
- 相关被写成因果；
- 常见做法被写成必然；
- 一种实现被写成唯一方式；
- 关键前提被省略。

纠偏后形成更稳定的模型。

### 形成自己的分析框架

最终要留下未来可以重复使用的判断方式，而不只是本次答案。

# 三、Knowledge Note

完整学习单元默认形成或更新 Knowledge Note；小问题无需强制生成。

Knowledge Note 没有固定模板，但应尽量实现这些功能：

- 我现在最核心的判断；
- 当前对象本身应被怎样理解，而不是只留下上位方法；
- 这件事所属的上位模型；
- 至少一个关键事件或机制；
- 会影响长期理解的纠偏；
- 我自己的分析框架；
- 可以迁移到相邻问题的认识。

最终笔记应能脱离原材料独立成立。

---

# 四、Find Gaps

Knowledge Model 建立后，只做一次轻量内部扫描。

只检查三类 Gap：

### 操作 Gap

> 我会解释，但如果明天真做，仍不知道第一步怎么开始。

### 验证 Gap

> 当前判断仍只是合理假设，还缺真实数据、案例、实验、反例或基线。

### 决策 Gap

> 这里不存在唯一答案，必须由业务、专家、技术或管理者做选择。

不要罗列所有“还没学的知识”。

优先保留：

> 不解决它，当前知识就无法继续进入真实行动的缺口。

---

# 五、Project to Use

先判断用户下一步要拿知识做什么，再决定如何表达 Gap。

核心原则只有一句：

> **把影响下一步的不确定性，转换成能推动下一步的输入。**

常见投影包括但不限于：

### 继续学习

自然打开当前最值得进入的一层，解释为什么值得继续追，并给出少量同层问题。

### 会议 / 专家交流

把 Gap 转成能够减少不确定性的讨论问题。

问题应尽量导向：

- 一个事实确认；
- 一个专家判断或业务假设；
- 一个设计选择；
- 一个后续建模或实施所需输入。

### 开始实施

转换为：

> 第一批输入 → 第一步动作 → 初版产物 → 如何验证 → 下一次迭代。

优先形成最小可验证闭环，而不是一次规划完整大工程。

### 方案 / 决策

转换为：

> 需要做出的选择 + 支撑证据 + 主要权衡 + 尚未确定的信息。

这些只是用途示例，不是固定模式列表。

---

# 六、输出原则

最终回答应该像自然形成的一套认识，而不是模板填表。

通常可以遵循：

`理解 → 纠偏 → 重构 → Knowledge Note → 根据用途继续推进`

但不要求显式出现这些标题。

只保留一个总约束：

> **内部可以有框架，外部必须保持自然；规则服务于理解与行动，而不是让用户看到规则本身。**

---

# 七、验收标准

一次高质量学习结束后，用户应得到：

1. 一套比输入材料更稳定、且没有因过度抽象而丢失对象本身的个人知识模型；
2. 对真正阻塞下一步的关键问题有清楚认识；
3. 当用户有明确下一步目标时，得到与该目标匹配的可用产物。

如果知识很多，但用户仍不知道“我现在到底怎么看这件事”或“下一步拿它干什么”，则 Skill 没有完成任务。
